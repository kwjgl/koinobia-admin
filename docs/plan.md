# 통합 앱 관리 페이지(koinobia-admin) 계획서

작성: 계획 일꾼 (2026-11-09). 사용자가 정한 것(9장)을 반영해 고쳤다. 계획서와 9장이 다르면 9장이 우선이다.
표시 약속: **[확인함]** = pray-for 코드에서 직접 읽은 것. **[메모]** = 사용자가 준 디다코 쪽 메모(디다코 저장소는 이 세션에 없음). **[추측]** = 확인 필요.
실제 비밀값·시트 주소는 이 계획서에 옮겨 적지 않았다.

---

## 1. 한눈에 보기

**무엇을**: 코이데·디다코·(나중에) 텔리오를 한곳에서 관리하는 "앱 관리 페이지"를 새 저장소 `koinobia-admin`에 따로 만든다.

**왜**
- 지금 앱 관리자 보기는 코이데 앱 안(`app/index.html`의 `?appadmin`)에 얹혀 있다. 디다코·텔리오가 늘면 코이데 안에서 다른 앱을 관리하는 모양이 어색해진다.
- 코이데 화면 파일이 5,700줄이라, 관리 화면을 고칠 때마다 코이데 전체를 건드리고 서비스워커 캐시 번호를 올리고 koide에 다시 올려야 한다.
- 관리 페이지는 코이데 앱과 다른 주소(다른 "문")에 두는 편이 안전하다. 앱 관리자의 로그인 표시가 일반 앱 화면과 섞이지 않는다.

**지금과 무엇이 달라지나**

| | 지금 (`?appadmin`) | 새 관리 페이지 |
|---|---|---|
| 화면 | 코이데 `app/index.html` 안 | 새 저장소의 작은 정적 페이지(빌드 없음) |
| 서버 | 코이데 기본 서버(pray-for `apps-script/hub/`) | **같은 기본 서버를 그대로 쓴다** (3장 추천) |
| 로그인 | 코이데 주소에서 카카오 로그인 | 새 주소에서 카카오 로그인(같은 `login` 요청) |
| 앱 | 코이데 + 디다코 칸 | 코이데 · 디다코 · 텔리오(자리) 칸 |

핵심: 처음에는 **서버 코드를 거의 안 바꾼다.** 화면만 옮기고, "이 교회로 들어가기"에 필요한 작은 요청 두 개만 기본 서버에 더한다.

## 2. 지금 앱 관리자 보기가 하는 일 (코드에서 확인한 것)

### 2-1. 화면(`app/index.html` 1914~1962줄 `appadmin`)

- 위쪽 요약 한 줄: "교회 N곳 · 테스트 공간 N곳 · 코드로 들어온 사람 N명" [확인함]
- **교회 카드**마다 아래가 나온다 [확인함]:
  - 상태 점(문제가 있으면 주황 점), 이름, "테스트"·"멈춤" 꼬리표, **고치기** 버튼
  - 교회 코드 칩들
  - 숫자 4칸: 부서 / 연결 / 코드로 온 사람 / 7일 오류
  - 할 일 꼬리표: 승인 기다림 N, 새 버전으로 배포 필요, 이번 달 기도제목 아직 없음, 승인 없이 바로 연결
  - 서버 버전 + 메모
  - **디다코 줄**: "디다코 서버 {버전} · 7일 오류 {수}", 못 물으면 "디다코 서버에 묻지 못했어요 · {까닭}"
  - 첫 관리자 초대 링크 상자(만든 카드에만): 링크, 복사, 닫기, "○○까지 한 번 쓸 수 있어요"
  - **이 교회로 들어가기** 버튼 (이 기기가 이미 쓰는 교회면 대신 "이 기기가 쓰는 교회" 꼬리표), **첫 관리자 초대 링크** 버튼
- **교회·테스트 공간 더하기·고치기 폼**: 이름, 이름표(처음에만), 종류(교회/테스트), 코드(쉼표로 여럿), 서버 주소, **디다코 서버 주소(비워도 됨)**, 메모, 멈춤 체크(고칠 때만) [확인함]
- 맨 아래: "기본 서버 {버전} · 내 카카오ID {값}" [확인함]
- 앱 관리자가 아니면 서버가 "앱 관리자만 볼 수 있어요. 내 카카오ID: …"라고 답한다. 이 숫자를 `APP_ADMINS`에 넣어 첫 관리자를 정하는 길이다 [확인함]

### 2-2. 기본 서버 요청(`apps-script/hub/Code.js`의 `HUB_ACTIONS`)

| 요청 | 보내는 값 | 받는 값 | 누가 쓰나 |
|---|---|---|---|
| `login` | `code`(카카오), `redirectUri` | `{token, nick}` (토큰 종류 `typ:'hub'`, 30일) | 모든 앱의 로그인. `redirectUri`가 `REDIRECT_URI` 목록에 있어야 함 |
| `admin` | `token` | `{me, version, churches:[{id,name,kind,codes,url,stopped,memo,came,status,err,didako,didakoStatus,didakoErr}]}` | **관리 화면** |
| `churchSave` | `token, orig, id, name, kind, codes, url, didako, memo, stopped` | 저장 뒤 `admin`과 같은 값 | **관리 화면** (앱 관리자만) |
| `enter` | `token, id, app` | `{church:{id,name,kind,url}, ticket}` | **관리 화면** "이 교회로 들어가기" |
| `invite` | `token, id` | `{link, until}` | **관리 화면** 첫 관리자 초대 |
| `where`, `peek`, `join` | — | — | 일반 사용자 입장(그대로 둠) |

- 앱 관리자 판정은 기본 서버 스크립트 속성 `APP_ADMINS`(카카오ID 목록)다 (`isAdmin_`) [확인함].
- **서버 상태는 이미 기본 서버가 대신 묻는다.** `adminView_`가 `UrlFetchApp`으로 코이데 교회 서버마다 `appStatus`를, 디다코 서버 주소가 있는 교회에는 디다코 `appStatus`를 같은 서명(`status|시각`)으로 보낸다 [확인함]. 디다코 쪽 답은 `{version, errors}`만 카드에 넘기고 나머지는 버린다 [확인함].
- 디다코 주소는 교회 시트 `교회` 탭의 맨 끝 칸 `디다코 서버 주소`에 있고, `churchSave`가 `https://script.google.com/…/exec` 모양인지 확인한 뒤 저장한다 [확인함].
- 확인증: `goTo_`가 코이데는 `typ:'ticket'`, 디다코는 `typ:'didako-ticket'`(`kakaoId, nick, church, exp 5분`)으로 `seal_`(base64WebSafe(JSON) + `.` + 서명)한다 [확인함]. 모양은 [메모]와 같다.

### 2-3. 무엇을 옮기고 무엇을 그대로 두나

**그대로 둔다 (서버 쪽, 1단계에서 바꾸지 않음)**: `login`, `admin`, `churchSave`, `invite`, 확인증 모양, `HUB_SECRET`, `REDIRECT_URI` 값(뒤에 주소를 더하기만), `where/peek/join`.

**옮긴다 (화면 쪽)**: 위 2-1의 모든 화면(요약·카드·폼·초대 상자·푸터).

**달라지는 점 두 가지**
1. "이 기기가 쓰는 교회" 꼬리표는 없앤다. 관리 페이지에는 "쓰는 교회"가 없다.
2. "이 교회로 들어가기"는 같은 브라우저 저장소를 쓰지 못한다. 코이데는 `koide.koinobia.com`, 관리 페이지는 다른 주소이기 때문이다. 그래서 작은 요청 두 개가 새로 필요하다(6장).

## 3. 가장 큰 갈림길과 추천

### (가) 화면만 새 저장소, 서버는 지금 기본 서버를 그대로 쓴다 (추천)
### (나) 관리용 서버도 새로 만든다

**코드로 확인한 사실**
- 로그인 확인(앱 관리자 확인)은 기본 서버의 `auth_` + `APP_ADMINS`다. 교회 목록(`교회` 탭), 사람 탭, `HUB_SECRET`도 모두 기본 서버(시트 + 스크립트 속성) 안에 있다 [확인함].
- 기본 서버의 `doPost`는 본문을 글자로 받아 JSON 답을 준다. 코이데가 다른 주소에서 이미 부르고 있다. 출처(origin) 검사는 없다. 그래서 새 주소의 페이지에서도 같은 방식(`fetch`, 본문은 글자 그대로)으로 부를 수 있다 [확인함. 새 주소에서 실제로 되는지는 1-1 PR의 실제 확인에서 다시 본다].

**(나)가 나쁜 까닭**
- 서명을 하려면 `HUB_SECRET`을 두 번째 서버에도 넣어야 한다. 비밀이 있는 곳이 늘어난다.
- `HUB_SECRET`은 로그인 확인증을 위조하는 열쇠이기도 하다. 새면 아무 카카오ID로 아무 교회·디다코에 들어갈 수 있다. 가능한 한 한곳에만 둔다.
- 교회 목록을 두 서버가 나눠 갖거나 한 서버가 다른 서버의 시트를 읽어야 해서 고장 지점이 늘어난다.
- 사용자가 새로 배포하고 속성을 맞출 것이 많아진다.

**(가)의 장점**: 1단계에서 사용자가 해야 할 서버 일이 거의 없다.
- 카카오 개발자 사이트에 새 주소 더하기
- 기본 서버 스크립트 속성 `REDIRECT_URI` 뒤에 새 주소 더하기 (속성은 값만 바꾸면 되고 코드 재배포는 필요 없다. 확인 필요)
- "이 교회로 들어가기" 때문에 기본 서버를 한 번 새 버전으로 배포

**(가)의 단점**: 서버 코드(`hub`)가 pray-for에, 화면이 koinobia-admin에 있어 두 저장소를 오간다. 3단계에서 `apps-script/hub/`를 새 저장소로 옮길지 다시 묻는다(9장 2번).

### 보안 판단 (반드시 지킬 것)
1. **디다코 `appStatus`는 반드시 서버(기본 서버)가 대신 부른다.** 서명(`HMAC(status|시각, HUB_SECRET)`)을 만들려면 `HUB_SECRET`이 있어야 한다. 브라우저에서 직접 부르면 비밀이 화면 파일에 들어가 누구나 가져간다. 지금 코드는 이미 서버가 대신 부른다. 새 페이지도 `admin`만 부르고 디다코 서버 주소로 직접 `fetch`하지 않는다.
2. 새 저장소에는 `HUB_SECRET`, `KAKAO_CLIENT_SECRET`, `APP_ADMINS` 값, 시트 주소를 두지 않는다. 화면 설정(`config.js`)에는 공개되어도 되는 값만 둔다: 기본 서버 웹 앱 주소, 카카오 REST API 키(원래 로그인 주소에 드러나는 공개 값), 새 페이지 주소, 앱 주소들.
3. 관리 페이지를 코이데·대문(`koinobia.com`)과 **다른 하위 주소**(`admin.koinobia.com`)에 둔다. 같은 주소 아래 경로(`koinobia.com/admin/`)에 두면 대문의 다른 스크립트와 브라우저 저장소를 나눠 쓰게 되어 앱 관리자 토큰이 더 쉽게 닿는다.
4. 서버가 보낸 글(교회 이름, 메모, 오류 까닭)은 모두 글자로만 화면에 넣는다. 코이데의 `esc()`처럼 HTML로 해석하지 않는다.
5. "이 교회로 들어가기"의 일회용 통행증은 주소의 `#` 뒤(fragment)에 싣는다. `#` 뒤는 서버 기록과 Referer에 남지 않는다. 받는 앱은 읽자마자 주소에서 지운다. 통행증은 5분, 한 번만 쓴다.

## 4. 새 저장소 구조

저장소: `kwjgl/koinobia-admin` (원격 주소 확인함). 지금은 커밋이 없고 원격에도 브랜치가 안 보인다 [확인함. 원격이 정말 비었는지는 확인 필요].

koinobia-admin/
├─ index.html          껍데기 한 장(제목 "코이노비아 앱 관리", noindex, 스크립트·CSS 연결)

├─ js/auth.js          카카오 로그인 이동, ?code 처리, 토큰 저장·지우기, 로그아웃
├─ js/app.js           화면 상태, 그리기, 클릭 처리(작게 유지)

├─ CNAME               admin.koinobia.com (GitHub Pages 사용자 지정 도메인. 지우지 않기)
├─ .gitignore
├─ README.md           이 저장소가 무엇인지, 주소, 사용자가 할 일 한눈에
├─ AGENTS.md           공통 규칙(코이데 것을 줄여서)
├─ CLAUDE.md           Claude만 따르는 것(코이데 CLAUDE.md의 일 나누기 규칙을 그대로)
└─ docs/
   ├─ design.md        이 페이지의 약속·화면·결정 기록(짧게)
   └─ setup.md         카카오·DNS·Pages·스크립트 속성 순서

**`config.js` 값**

| 이름 | 뜻 | 비고 |
|---|---|---|
| `HUB_URL` | 기본 서버 웹 앱 주소 | 사용자가 값을 줘야 함. 코이데 koide의 config와 같은 값 |
| `KAKAO_REST_KEY` | 카카오 REST API 키 | 공개 값. Client Secret은 절대 넣지 않음 |
| `REDIRECT_URI` | 이 페이지 주소(끝 `/` 포함) | 예 `https://admin.koinobia.com/` |
| `APPS` | 앱별 시작 주소 | 코이데 `https://koide.koinobia.com/app/`, 디다코 `https://didako.koinobia.com/note/` ([메모]에서 확인) |
| `NEED_SERVER` | 코이데 화면이 바라는 서버 버전 앞 날짜 | 지금 `2026-11-08`. 코이데 `app/index.html`의 `NEED_SERVER`와 같게 손으로 맞춘다(규칙 파일에 적기) |

**왜 이렇게**
- 프레임워크·빌드 없이 파일 몇 개: 사용자가 GitHub Pages로 바로 열 수 있고, 코이데와 같은 방식이다.
- 서비스워커·홈 화면 앱은 두지 않는다(관리 화면은 늘 새 데이터를 봐야 하고, 캐시 번호 규칙이 새로 생기는 것을 피한다). 대신 `config.js`에 화면 버전을 한 줄 두고 푸터에 보인다.
- 배포 주소 후보: (a) `admin.koinobia.com` — 가비아 DNS에 `CNAME admin → kwjgl.github.io.` 한 줄, Pages에 사용자 지정 도메인(추천) / (b) `kwjgl.github.io/koinobia-admin/` — DNS 필요 없지만 카카오가 경로를 받는지 확인 필요 / (c) `koinobia.com` 아래 경로 — 3장 보안 3번 때문에 비추천.

**규칙 파일**: 필요하다. AI가 이 저장소에서 일할 때 길을 잃지 않게 한다.

## 5. 화면 설계

### 5-1. 모양: 코이데 것을 복사해서 쓴다
- `app/index.html` 21~46줄의 색 변수(`--page --surface --surface-2 --ink --ink-2 --line --line-strong --accent --accent-mid --accent-soft --on-accent --warn --warn-soft` 등)를 `css/admin.css`로 **복사**한다. **먹색 테마(늘 밝게)**: 먹색(ink) 테마의 밝은 값을 `:root`에 고정하고 `color-scheme: light`. 어두운 모드와 기기 설정 분기는 두지 않는다. 코이데의 5가지 색 테마와 4가지 디자인 스타일(basic·new·classic·glass)은 가져오지 않는다(새 색을 만들지 않는다). 글꼴·크기도 코이데와 같게(Gowun Batang 제목, IBM Plex Sans KR 본문, 휴대폰 16px, PC 15px).
- `.card .btn .btn.ghost .btn.small .link .field .hint .eyebrow .ch-todo .own-tag .ops-dot .aa-*`(index.html 1003·1090~1116줄 근처)의 규칙을 같은 이름으로 복사한다. 새 버튼·카드는 이 중 비슷한 것을 본뜬다.
- 터치 영역 44px 이상, 휴대폰 한 줄 / PC 카드가 나란히(`aa-grid`의 `repeat(auto-fill, minmax(min(100%, 320px), 1fr))`).
- 이모지·장식은 넣지 않는다(설계서 9장: 더보기·관리 화면에는 이모지를 넣지 않는다).
- 순위·정렬·"가장 많은"·그래프·교회끼리 비교하는 표시는 넣지 않는다. 카드 순서는 시트 순서 그대로.
- 코이데 모양이 바뀌면 이 복사본을 손으로 맞춘다(규칙 파일에 적기).

### 5-2. 화면 흐름
1. **로그인 전**: 제목 "코이노비아 앱 관리", 한 줄 안내 "앱 관리자만 들어올 수 있어요", 카카오로 로그인 버튼.
2. **앱 관리자가 아닐 때**: 서버의 문장("앱 관리자만 볼 수 있어요. 내 카카오ID: …")을 그대로 보인다. 첫 관리자를 `APP_ADMINS`에 넣는 길이라 반드시 남긴다. + 로그아웃 버튼.
3. **교회 카드 목록**: 위 요약 한 줄, 카드 격자, 맨 끝 점선 "+ 교회·테스트 공간 더하기", 푸터(기본 서버 버전·내 카카오ID·화면 버전·로그아웃).
4. 위쪽에 앱 이름 칸 구분은 두지 않는다(1단계). 3단계에서 앱별 칸이 생기면 카드 안에서 나눈다.

### 5-3. 교회 카드 안의 앱 칸
카드 한 장 안에 칸 세 개를 둔다. 1단계에서는 코이데·디다코만 채운다.

| 칸 | 내용 (1단계) |
|---|---|
| **코이데** | 지금 카드 그대로: 숫자 4칸, 할 일 꼬리표, 서버 버전, 메모 |
| **디다코** | 서버 주소가 있으면 "디다코 서버 {버전} · 7일 오류 {수}". 못 물으면 **"답이 없어요"** + 까닭 작은 글씨. 주소가 비면 "쓰지 않아요"(회색). **연결 수·사람 수·기록 수는 없다** |
| **텔리오** | 자리만: "준비 중"(회색, 눌러도 아무 일 없음). 서버 칸·요청은 만들지 않는다 |

- 상태 점(`ops-dot`)은 코이데·디다코 중 하나라도 이상하면 주황(지금 코드와 같은 규칙).
- "답이 없어요": 서버가 `didakoStatus:null`이고 `didakoErr`가 있을 때. 주소가 틀렸거나 서버가 꺼진 경우다.
- **테스트 공간**(종류 테스트, 이름표 `TEST`)도 같은 카드에 "테스트" 꼬리표만 붙는다. 디다코 칸도 같다.

### 5-4. 버튼
- **고치기 / 더하기**: 폼은 지금과 같다(디다코 서버 주소 칸 포함). 이름표는 처음에만. 저장 실패하면 쓰던 값을 그대로 둔다.
- **이 교회로 들어가기**: 앱별 버튼 두 개 — 코이데로 / 디다코로. 디다코 버튼은 서버 주소가 있는 교회에만 보인다. 누르면 새 탭에서 해당 앱이 열리고 그 교회로 들어가진다(6장 `enterPass`). 기본 서버의 `enter`가 하던 것과 같은 효과: 사람 탭은 바꾸지 않는다.
- **첫 관리자 초대 링크**: 지금과 같다(7일, 한 번, 링크에 교회 코드). 링크 바탕은 서버가 `REDIRECT_URI`의 첫 주소(코이데)로 만든다 [확인함]. 이 때문에 `REDIRECT_URI`를 쓸 때 **코이데 주소가 첫째 자리에 남아야 한다**.
- 디다코 교회 관리자를 누가 세우나는 3단계 질문(9장 7번).

### 5-5. 확인용 데모
카카오 로그인은 실행 일꾼이 할 수 없다. `?demo`로 열면 `js/demo.js`가 가짜 응답(지어낸 교회 3곳: 정상 / 디다코 답 없음 / 멈춤 테스트)을 주어, 휴대폰·PC 화면을 스크린샷으로 볼 수 있게 한다. 실제 로그인 확인은 사용자가 한다.

## 6. 서버 쪽 바꿀 것

### 6-1. 1단계에서 새로 필요한 기본 서버 요청 두 개 (pray-for `apps-script/hub/Code.js`)
요청 이름은 제안이다 [추측: 사용자 확인 필요].

**`enterPass`** — 관리 페이지가 부른다. 앱 관리자만.
- 보내는 값: `token`(기본 서버 로그인 표시), `id`(교회 이름표), `app`(`'koide'` 또는 `'didako'`)
- 하는 일: `isAdmin_` 확인. 교회를 찾고, 디다코인데 주소가 비었으면 기존 `notYet_()`로 거절. 통행증을 `seal_({typ:'enter-pass', kakaoId, nick, church: id, app, exp: 지금 + 5분})`로 만든다. **교회 서버 주소나 확인증 자체는 통행증에 넣지 않는다.**
- 받는 값: `{ pass, name }`
- 관리 페이지는 `APPS[app] + '#enter=' + pass`를 새 탭으로 연다.

**`enterOpen`** — 코이데 앱(과 디다코 노트)이 부른다. 로그인 없이(통행증이 열쇠).
- 보내는 값: `pass`, `app`
- 하는 일: `open_(pass)`로 서명을 확인. `typ === 'enter-pass'`, 유효 시간, `app` 일치. `CacheService`에 통행증 서명 부분으로 "사용함" 표시(10분)를 남기고 두 번째 사용은 `fail_('login', ...)`. 교회 주소는 **그 순간 시트에서 다시 읽어** 기존 `goTo_(a, c, app)`을 부른다.
- 받는 값: 기존 `enter`와 같은 `{church:{id,name,kind,url}, ticket}` (디다코는 `didako-ticket`).

**왜 이렇게 두 개로 나눴나**: 주소에 교회 서버 주소를 직접 실으면 가짜 링크로 사용자를 가짜 서버로 보낼 수 있다. 그래서 주소에는 서명된 불투명한 통행증만 싣고, 서버 주소는 기본 서버가 알려 준다. 통행증 종류(`enter-pass`)는 `hub`·`ticket`·`didako-ticket`과 달라서 어느 서버도 로그인 표시나 확인증으로 오해하지 않는다 [확인함: `auth_`는 `typ:'hub'`, `ticketLogin_`은 `'ticket'`만 받는다].

받는 쪽 일(각자 앱 저장소에서):
- **코이데** `app/index.html` `boot()`: `location.hash`에 `#enter=…`가 있으면 즉시 주소에서 지우고(`history.replaceState`) `hubApi('enterOpen', {pass, app:'koide'})` → 기존 `enterChurchServer(w)` 호출. (HUB일 때만)
- **디다코 노트**(gbs 저장소): 같은 방식으로 `#enter=`를 받아 `enterOpen`(`app:'didako'`)을 부르고 받은 확인증으로 자기 서버에 로그인한다. 이 일은 디다코 저장소에서 따로(7장 1-6).

### 6-2. 바뀌면 안 되는 것
- 확인증 모양과 서명: `typ:'ticket'` / `typ:'didako-ticket'`, `kakaoId`, `church`, `exp`(5분), `base64WebSafe(JSON) + '.' + base64WebSafe(HMAC-SHA256(앞부분, HUB_SECRET))`. `seal_`·`sign_` 함수를 고치지 않는다.
- `HUB_SECRET` 값은 바꾸지 않는다. 새 저장소·새 서버에 복사하지 않는다.
- `REDIRECT_URI`에는 `https://didako.koinobia.com/note/`가 계속 들어 있어야 한다 [메모]. 새 주소는 **맨 뒤에 더하기만** 한다. 첫째(코이데)는 그대로.
- 디다코 `appStatus`의 서명(`status|` + `at`)과 받는 값 `{version, errors}`, 요청 시각 ±5분.
- `churchSave`가 디다코 칸을 "안 오면 그대로 둔다"는 동작.

### 2단계: 교회를 나갈 때 (디다코 쪽 요청이 생긴 뒤)

**전제**: 디다코 저장소에 새 요청이 먼저 있어야 한다. 이름·서명은 [메모]의 예시: `memberLeave` — 보내는 값 `kakaoId`, `at`(밀리초), `sig` = `HMAC(leave|kakaoId|at)`(base64WebSafe), 받는 값 `{ok:true}`, 요청 시각 ±5분. 이 요청 자체는 디다코 저장소가 만든다. 나가기 전 내려받기 안내는 디다코 앱 화면이 한다.

**기본 서버에 더할 것(제안, [추측])**: `leave` — 본인이 나갈 때(기본 서버 로그인 표시 `token`).
1. 사람 탭에서 이 사람의 교회를 찾는다.
2. 그 교회에 디다코 서버 주소가 있으면 `memberLeave`를 서버가 대신 보낸다(`UrlFetchApp`, `HUB_SECRET`으로 서명). 브라우저가 직접 부르지 않는다.
3. 성공(`{ok:true}`)이면 사람 탭의 줄을 지운다(지금 `hub/Code.js`에는 줄을 지우는 함수가 없으므로 `remove_`를 더한다 [확인함]).
4. 실패하면 줄을 지우지 않고 "지금은 못 지웠어요. 잠시 뒤 다시 해 주세요."로 답한다. **재시도 목록(누가 나갔는지 적어 두기)은 만들지 않는다.** 흔적을 남기지 않기 위해서다.
5. 개수도 남기지 않는다: 로그·시트에 나간 사람 수를 적지 않는다. 사람 탭의 "코드로 온 사람" 숫자는 줄을 지우면 저절로 준다.

**코이데 쪽**: 코이데 교회 서버의 명단·기록 삭제는 pray-for의 별도 기능이다(지금 설계서에 나가기 기능이 없음 [확인함]). 기본 서버가 코이데 교회 서버에 같은 방식의 요청(예 `hubMemberLeave`, 서명 `leave|kakaoId|at`)을 보내는 쪽으로 합치는 것을 추천한다. 그러면 앱은 기본 서버 `leave` 하나만 부르면 되고, 코이데·디다코가 따로 지워져 반쯤 남는 일이 없다. 이 부분은 pray-for에서 따로 계획을 세운다(9장 9번).

**나가기 직후 새 로그인 때** 기본 서버가 교회 서버들에 `hubKnows`를 물어 사람 탭을 다시 채우는 길이 있다(`whereOf_`) [확인함]. 그래서 교회 서버의 삭제가 반드시 먼저여야 한다(그렇지 않으면 삭제한 사람이 다시 나타난다).

### 3단계: 나중 (GBS 공동체용 시작 때)
지금은 묻기만 하고 만들지 않는다. 시작할 때 따로 계획서를 쓴다. 정할 것:
- 교회 카드에 **앱별 칸**(코이데·디다코·텔리오). 디다코는 "서버 주소 있으면 켜짐". 텔리오 칸의 서버 칸은 교회 탭에 열을 더할지(예 `텔리오 서버 주소`) 이때 정한다.
- **구독 상태**: 공용 바닥의 교회에 둔다 → 카드 자리만 비워 두고 금액·무료 기준은 미정 [메모]. 순위·비교로 보이지 않게 카드 안의 한 줄 상태로만.
- **디다코 교회 관리자를 누가 세우나**: 코이데 관리자 겸직 vs 앱마다 따로. 따로라면 초대 링크에 앱 표시(`app=didako`)를 붙이고 `invite`에 `app`을 받게 한다. 관리 페이지는 앱 관리자 일과 **첫 교회 관리자 세우기까지만**(역할 위계: 앱 운영자[=화면 이름 앱 관리자] › 교회 관리자 › 부서 관리자 › 리더·코리더 › 회원) [메모].
- **Supabase로 갈아 끼우는 방법**: 서버 부르기는 `js/api.js` 한 파일에만 있으므로 그 안쪽만 Supabase로 바꾼다(`app.js`는 그대로). 앱 관리자 확인은 Supabase 역할(role)로 한다. 비밀 열쇠가 필요한 일(디다코 서버 상태 묻기, 통행증 서명 등)은 Supabase 서버 함수가 대신 하고 브라우저에는 열쇠를 두지 않는다.
- **Supabase 정식 서비스**: 사람·교회·부서·사랑방·관리자 역할·교회 코드는 공용 바닥, 디다코만의 것은 디다코 방. 이때 관리 페이지가 공용 바닥을 본다. 기본 서버를 새 저장소로 옮길지도 이때 정한다(지금은 설계서 13장에서 새 서버 계획이 "뒤로 미룸" 상태 [확인함]).

## 9. 사용자가 정한 것 (2026-11-09)

1. 저장소는 **공개**. 주소는 `admin.koinobia.com`(GitHub Pages, `CNAME` 파일).
2. 서버는 지금 **기본 서버(pray-for `apps-script/hub/`)를 그대로** 쓴다. 새 서버 없음. 기본 서버 코드는 당분간 pray-for에 두고 3단계에서 옮길지 다시 정한다.
3. "이 교회로 들어가기"는 **일회용 통행증(`enterPass`/`enterOpen`)** 방식이다. 1-1 PR에서는 만들지 않는다(1-4, 1-5).
4. 화면 색은 **먹색 테마(늘 밝게)**. 코이데 먹색 테마의 밝은 값을 고정하고 어두운 모드는 두지 않는다. 기기 설정과 상관없이 늘 밝다.
5. 옛 `?appadmin`은 새 페이지가 확인되면 바로 없앤다(한 주 기다리지 않음, 1-7).
6. 관리자가 명단에서 사람을 뺄 때 **디다코 기록은 지우지 않는다**. 지우기는 본인이 나갈 때만 한다.
7. 디다코 교회 관리자를 누가 세울지는 **3단계에서** 정한다. 당분간 앱 운영자가 겸한다.
8. Supabase로 바꿀 때를 대비해 **서버 부르기는 `js/api.js` 한 파일에만** 둔다. 화면 코드는 `api.admin()`, `api.login(code)`처럼 뜻으로만 부른다.
9. 나가기(2단계)는 기본 서버가 코이데·디다코 서버에 모두 보내고 한 곳이라도 실패하면 아무것도 안 지우고 다시 하라고 한다(재시도 목록 없음). 텔리오 칸은 "준비 중" 자리만 둔다. 탭 제목은 "코이노비아 앱 관리".
